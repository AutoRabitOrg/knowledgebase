# Event Types

The following is a complete list of ARM event types written to the SIEM/CEF audit log when audit logging is enabled. Event type names match the internal `CEFEvents` enum exactly so they can be used as the `eventType` filter value in the [Retrieval APIs](https://knowledgebase.autorabit.com/product-guides/arm/security-information-and-event-management/retrieval-apis).

> **Note:** Audit logging is disabled by default. Customers must enable the organization audit setting and the CEF logging toggle for events to be written. These settings are not exposed in the product UI.

### Create User Event Details

When an administrator creates a user account, ARM writes a `USER` event with `arDBOperation=Create User`. The actor recorded is the administrator who performed the creation (not the new user).

Example CEF fields (illustrative):

```
USER | arDBOperation=Create User | arActor=<admin-email> | arStatus=Success
msg=User created via <source>: email, login name, user ID, organization, role, status (active/inactive)
```

This event is written for the following flows:

* Admin > Users > Add User (new UI, classic UI, and REST `/user/creation`)
* Admin > Users > Import Users from AD
* Subscriptions > Create Team (team admin account)
* Create/Edit Team with grant access
* Edit Team > replace team admin with a new account
* Add released user to a team
* Channel Secure sign-in (on-prem automatic provisioning)
* Self sign-up / enterprise registration (new org’s first Super Admin)

Creating an active user typically produces both a Create User event and a subsequent Activate/Deactivate event.

All values in the event are escaped to prevent injection of additional audit lines or fields.

### Notes for SIEM Consumers

* Use the exact event type strings from the table above when filtering with the Retrieval APIs (`eventType` query parameter).
* The first ten rows (LOGIN through SALESFORCESETTINGS) are the events most commonly monitored by security teams.
* Existing events for delete, activate, deactivate, permission changes, and role changes continue to be written as before.
* Timestamp formats may vary across event types within the same log file (known limitation; tracked separately).
