# Storage and KMS User Guide

## Vault Connect: Storage and KMS Configuration

Configuration guide

This guide explains how to grant AutoRABIT Vault Connect access to your AWS storage and encryption resources. Follow the option that matches your setup:

* **Option 1:** Fully AutoRABIT-managed storage and processing engines. No configuration required.
* **Option 2:** Customer-owned S3 bucket encrypted with a customer-owned KMS key.
* **Option 3:** AutoRABIT-managed storage encrypted with a customer-owned KMS key.

{% hint style="warning" %}
**Important:** Complete your storage and KMS setup before Vault Connect is enabled. The AutoRABIT access role is created only once, when the Vault Connect settings page is first opened, and it is based on the backup storage and KMS key configured at that time. Make sure the S3 bucket, region, and KMS key settings in AutoRABIT Vault are correct and final before enabling Vault Connect.
{% endhint %}

{% hint style="info" %}
**Prerequisites (Options 2 and 3):** AWS console access with permission to edit S3 bucket policies, lifecycle rules, and KMS key policies.
{% endhint %}

{% hint style="info" %}
**Note:** Account IDs, role ARNs, bucket names, key IDs, and user details are masked in the screenshots. Always copy the policies directly from your Vault Connect screen; they are generated specifically for your account.
{% endhint %}

## Option 1: Fully AutoRABIT-Managed (No Configuration Required)

Use this option when AutoRABIT manages both the backup storage and the processing engines. Vault Connect is enabled automatically. No bucket policy, KMS key policy, or lifecycle rules are required.

### Verify that Vault Connect is enabled

{% stepper %}
{% step %}
### Go to Vault Connect

In AutoRABIT Vault, go to **Settings > Vault Connect**.
{% endstep %}

{% step %}
### Confirm the configuration

Confirm that the status shows **Enabled** and the configuration route is **AutoRABIT-managed storage > AutoRABIT-managed engines**.

&#x20;                         Vault Connect enabled with AutoRABIT-managed storage and engines
{% endstep %}
{% endstepper %}

## Option 2: Customer-Owned S3 Bucket and KMS Key

Use this option when Vault Connect reads backups from an S3 bucket in your AWS account that is encrypted with your own customer-managed KMS key (SSE-KMS).

{% stepper %}
{% step %}
### Copy the AutoRABIT access role and bucket policy

In AutoRABIT Vault, go to **Settings > Vault Connect**. In **Grant storage access**, review the storage summary and the AutoRABIT access role ARN.

<figure><img src="../../../../.gitbook/assets/image (3239).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Vault Connect – Grant storage access

Under **1. Add bucket policy**, click the eye icon to review the policy, then click **Copy Policy**.

<figure><img src="../../../../.gitbook/assets/image (3240).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Bucket policy generated by Vault Connect
{% endstep %}

{% step %}
### Apply the bucket policy in AWS S3

In the AWS console, open **Amazon S3 > Buckets >** your bucket **> Permissions**.

Under **Bucket policy**, click **Edit**, paste the copied policy, and click **Save changes**. If the bucket already has a policy, add the Vault Connect statements to the existing policy instead of replacing it.

<figure><img src="../../../../.gitbook/assets/image (3241).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Bucket policy applied in AWS S3
{% endstep %}

{% step %}
### Copy the KMS key policy

Back in Vault Connect, under **2. Add KMS key policy**, click the eye icon to review the policy, then click **Copy Policy**.

<figure><img src="../../../../.gitbook/assets/image (3242).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                KMS key policy generated by Vault Connect
{% endstep %}

{% step %}
### Apply the KMS key policy in AWS KMS

In the AWS console, open **KMS > Customer managed keys**, select the key used by the bucket, and click **Edit policy**.

Add the copied statement to the Statement array of the existing key policy and click **Save changes**. Do not remove the existing statements (for example, Enable IAM User Permissions).

<figure><img src="../../../../.gitbook/assets/image (3243).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                KMS key policy updated in AWS KMS
{% endstep %}

{% step %}
### Review the recommended lifecycle rules

In Vault Connect, under **Recommended lifecycle rules**, click **View rules** to see the lifecycle guidance.

<figure><img src="../../../../.gitbook/assets/image (3244).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Recommended lifecycle rules

| **Lifecycle rule name**       | **Prefix**                | **Expire after** |
| ----------------------------- | ------------------------- | ---------------- |
| vault-connect-staging-expiry  | vault-connect/staging/    | 7 days           |
| vault-connect-progress-expiry | vault-connect/\_progress/ | 1 day            |
{% endstep %}

{% step %}
### Create the lifecycle rules in AWS S3

In the AWS console, open your bucket, go to **Management > Lifecycle rules**, and click **Create lifecycle rule**. Create both rules below.

#### Rule 1: vault-connect-staging-expiry

Enter the rule name vault-connect-staging-expiry, select **Limit the scope of this rule using one or more filters**, and enter the prefix vault-connect/staging/.

<figure><img src="../../../../.gitbook/assets/image (3245).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Rule 1 – name, scope, and prefix

Under **Lifecycle rule actions**, select **Expire current versions of objects**, set **Days after object creation** to **7**, and save the rule.

<figure><img src="../../../../.gitbook/assets/image (3246).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Rule 1 – expire after 7 days

#### Rule 2: vault-connect-progress-expiry

Enter the rule name vault-connect-progress-expiry, select **Limit the scope of this rule using one or more filters**, and enter the prefix vault-connect/\_progress/.

<figure><img src="../../../../.gitbook/assets/image (3247).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Rule 2 – name, scope, and prefix

Under **Lifecycle rule actions**, select **Expire current versions of objects**, set **Days after object creation** to **1**, and save the rule.

<figure><img src="../../../../.gitbook/assets/image (3248).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Rule 2 – expire after 1 day

Confirm that both rules appear as **Enabled** in the lifecycle rules list.

<figure><img src="../../../../.gitbook/assets/image (3249).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Lifecycle rules enabled on the bucket
{% endstep %}

{% step %}
### Verify and activate

In Vault Connect, click **Continue to Verification**.

<figure><img src="../../../../.gitbook/assets/image (3250).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Continue to Verification

Vault Connect assumes the access role, checks read/write access to the bucket, and runs a test Athena query. This usually takes less than a minute.

<figure><img src="../../../../.gitbook/assets/image (3251).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Verification in progress

When all checks pass, the status changes to **Verified** and Vault Connect is active.

<figure><img src="../../../../.gitbook/assets/image (3252).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Connection verified

{% hint style="info" %}
**Note:** If verification fails, Vault Connect identifies the denied resource and the checks that did not run. Review the bucket policy, KMS key policy, and lifecycle rules, then click Re-verify Connection.
{% endhint %}
{% endstep %}
{% endstepper %}

## Option 3: AutoRABIT-Managed Storage with Customer-Owned KMS Key

Use this option when your backups are stored in AutoRABIT-managed storage but encrypted with a KMS key in your AWS account. Only the KMS key policy is required.

{% stepper %}
{% step %}
### Open the managed configuration

In AutoRABIT Vault, go to **Settings > Vault Connect**. Under **Grant access to your KMS key**, review the AutoRABIT access role ARN.

<figure><img src="../../../../.gitbook/assets/image (3253).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Vault Connect – Grant access to your KMS key
{% endstep %}

{% step %}
### Copy the KMS key policy

Under **Add KMS key policy**, click the eye icon to review the policy, then click **Copy Policy**.

<figure><img src="../../../../.gitbook/assets/image (3254).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                KMS key policy generated by Vault Connect
{% endstep %}

{% step %}
### Apply the KMS key policy in AWS KMS

In the AWS console, open **KMS > Customer managed keys**, select your key, and click **Edit policy**.

Add the copied statement to the Statement array of the existing key policy and click **Save changes**.

<figure><img src="../../../../.gitbook/assets/image (3255).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                KMS key policy updated in AWS KMS
{% endstep %}

{% step %}
### Verify and activate

In Vault Connect, click **Verify Connection**.

<figure><img src="../../../../.gitbook/assets/image (3256).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Verification in progress

When all checks pass, the status changes to **Verified** and Vault Connect is active.

<figure><img src="../../../../.gitbook/assets/image (3257).png" alt=""><figcaption></figcaption></figure>

&#x20;                                                Connection verified
{% endstep %}
{% endstepper %}
